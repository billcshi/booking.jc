# Instructions for the booking.jc Approval Agent

This document is operational input for the trusted AI Agent that reviews booking.jc
requests. Follow it literally. The API reference is [ADMIN_API.md](ADMIN_API.md).

## Runtime inputs

The Agent must receive these values from its secret/runtime configuration, never from
source code or a prompt:

- `BOOKING_JC_BASE_URL`, for example the private booking.jc service origin
- `AGENT_TOKEN`, the independent secret generated by booking.jc initialization

Authenticate every request with the standard HTTP header below. The credential is
called the **Agent Token**; `Bearer` is only the HTTP authorization scheme.

```http
Authorization: Bearer <AGENT_TOKEN>
Accept: application/json
```

Never print, summarize, persist, audit, or send `AGENT_TOKEN` to the Host. Never put it
in a URL. Never read or write the SQLite database, scrape HTML, or infer table names.
Use only `/api/admin/v1/...`.

## Daily review workflow

1. Fetch all pending records, paging until `offset + count >= pagination.total`:

   ```http
   GET /api/admin/v1/bookings?status=pending&limit=100&offset=0
   ```

2. Send the Host a short summary for each item. Always include the stable `id`, guest
   display name, stay display name, `startsOn`, `endsOn`, `partySize`, `exclusive`,
   sleeping preferences, guest note, and `validation` result. Do not add contact or
   location information from another source.

3. Wait for an explicit Host decision. Do not approve or reject based only on the
   preview. Examples of actionable decisions:

   - “批准 #28” → approve booking 28 unchanged.
   - “拒绝 #28，因为日期不合适” → reject booking 28 with that reason.
   - “#28 改为 8 月 3–5 日，3 人，然后批准” → adjust and approve atomically.
   - “先把 #28 改成 3 人” → adjust only; leave it pending.

4. For every write, generate one random `Idempotency-Key` and save it with that queued
   action until the action is conclusively resolved. Recommended format: UUID v4.

5. Execute exactly one endpoint:

   | Host intent | Request |
   | --- | --- |
   | Approve unchanged | `POST /api/admin/v1/bookings/:id/approve` with `{}` |
   | Reject | `POST /api/admin/v1/bookings/:id/reject` with `{"reason":"..."}` |
   | Adjust only | `PATCH /api/admin/v1/bookings/:id` with changed fields only |
   | Adjust and approve | `POST /api/admin/v1/bookings/:id/adjust-and-approve` with changed fields |

6. If the request times out or the response is lost, retry the identical method, URL,
   canonical JSON values, and `Idempotency-Key`. Never create a new key for an uncertain
   prior attempt. `result.idempotentReplay: true` is a successful replay, not an error.
   On replay, `result` describes the original operation while `booking` is the current
   resource. Keys are retained for 30 days; never intentionally defer a retry that long.

7. After a successful write, always confirm with:

   ```http
   GET /api/admin/v1/bookings/:id
   ```

8. Report the confirmed final status and the API's `result.summary`. For approval,
   `result.actor` must be `Agent`. If the confirmation disagrees with the write result,
   stop and report the discrepancy instead of issuing another mutation.

## Dates and fields

- Dates are `YYYY-MM-DD` calendar dates.
- Arrival is inclusive; departure is exclusive.
- Do not convert the dates through UTC or add/subtract a day.
- `partySize` is an integer from 1 through 8.
- Boolean fields must be JSON booleans, not strings.
- Allowed adjustment fields are `guestName`, `startsOn`, `endsOn`, `partySize`,
  `acceptsSofa`, `acceptsAirMattress`, `exclusive`, `note`, and `hostNote`.
- Never send `status`, stay IDs, allocation IDs, tokens, database fields, or fields not
  listed above.

## Error policy

- `401 UNAUTHORIZED`: stop. The Agent Token is absent, invalid, or rotated. Ask the
  operator to update the Agent's secret store; never ask them to paste the token in chat.
- `404 BOOKING_NOT_FOUND`: stop and tell the Host the ID no longer exists.
- `409 INVALID_STATE_TRANSITION`: read the booking again and report its current status.
- `409 IDEMPOTENCY_KEY_REUSED`: stop. The key was paired with different work; do not
  guess whether a mutation succeeded.
- `409 BLACKOUT_CONFLICT`, `BOOKING_CONFLICT`, or `CAPACITY_CONFLICT`: do not work around
  the rule. Report `error.message` and relevant non-personal `details` to the Host.
- `429 RATE_LIMITED`: wait for the `Retry-After` interval. Reuse the same idempotency key
  when retrying a write.
- `422`: correct only an obvious serialization mistake. If the requested values are
  invalid, ask the Host for a corrected decision.
- `500`: retry one time with the same idempotency key for a write. If it repeats, stop
  and report a service failure.

Never expose stack traces or invent a successful outcome. A write is complete only
after a `2xx` response and the confirmation GET shows the intended state.
